# Release operations

## First integration

1. Push this project as a dedicated GitHub repository. `scripts/publish_github.ps1` prepares guarded private publication to `rvnsre/NotchPulse` using an already authenticated GitHub CLI. It validates the account, working tree, branch and origin and never force-pushes. Preserve the leading dot in `.github`.
2. Install native prerequisites, resolve dependencies using `cargo generate-lockfile`, review the graph and commit `Cargo.lock`.
3. Workflows honor a committed lockfile and check it with `cargo metadata --locked`; they bootstrap a graph only when no lockfile exists. The release job passes one shared lockfile to every packaging host.
4. Let `Verify` pass on Linux, Windows and macOS. Fix any compiler/platform integration findings before tagging. The authoring environment could not execute Rust builds.
5. Complete the manual acceptance and performance protocols on release hardware.

## Artifacts

| Build runner | Target | Deliverables |
| --- | --- | --- |
| Windows | `x86_64-pc-windows-msvc` | NSIS setup EXE, separate `NotchPulse-windows-x64.exe`, SHA256SUMS |
| macOS | `universal-apple-darwin` | Universal ARM64 + x86_64 DMG, SHA256SUMS |
| Ubuntu 22.04 | `x86_64-unknown-linux-gnu` | RPM, SHA256SUMS |

The release workflow resolves one dependency graph, compiles on native hosts, validates both Mac architectures using `lipo`, asserts artifact existence, then stages checksums. Tag/workspace/config versions must agree. All matrix jobs must succeed before a draft release is created. Release notes are generated by GitHub. A rerun uploads files to the existing tag release rather than failing on duplicate assets.

## Signing

For signed and notarized macOS builds, configure repository Actions secrets:

- `APPLE_CERTIFICATE`: base64-encoded Developer ID Application certificate (`.p12`).
- `APPLE_CERTIFICATE_PASSWORD`: certificate import password.
- `APPLE_SIGNING_IDENTITY`: Developer ID Application identity.
- `APPLE_ID`, `APPLE_PASSWORD` (app-specific password), and `APPLE_TEAM_ID`: notarization credentials.

Without those credentials, expect unsigned test artifacts and Gatekeeper warnings. NotchPulse uses Tauri's private macOS API support for transparent windows and targets direct distribution, not a promised Mac App Store submission.

Windows Authenticode signing depends on your certificate provider. Configure Tauri's Windows signing command/certificate options for that provider before packaging. Ensure the standalone EXE **and** installer are signed, timestamped, and verified with `signtool verify /pa`. Never put certificate passwords in workflow YAML or source. Windows signing is not falsely marked configured in this template.

An RPM signature is separate from an application code signature. To distribute through an enterprise repository, sign RPMs using your release key, publish repository metadata, and test install/upgrade/uninstall against your supported OS image. SHA-256 checksums detect accidental corruption; they are not a substitute for signatures.

## Platform compatibility

The Windows standalone EXE requires an already installed WebView2 Evergreen runtime; the NSIS bundle is configured to download its bootstrapper. A downloaded runtime requires connectivity at install time.

The RPM baseline is Ubuntu 22.04/glibc 2.35. Explicit dependencies include WebKitGTK 4.1, GTK3 and a GTK3 app-indicator implementation. RHEL 8/9 cannot be assumed compatible. Validate enterprise Linux versions, package naming, GTK/WebKit ABI and compositor behavior before advertising support. A rebuild against an approved older baseline or a target-native enterprise container may be needed.

## Publish

Update `workspace.package.version` and `src-tauri/tauri.conf.json` together. Commit source and lockfile, push `main`, wait for verification, then push `v<version>`. Inspect downloaded artifacts, verify signatures and checksums, complete platform acceptance, and publish the generated draft release. The workflow intentionally does not publish it without that review.
